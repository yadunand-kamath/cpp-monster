# GP-1 — Algorithmic Trading System (Indian Cash Equity Markets)

**Tier:** Grand Project · **Category:** Networking · **Est. effort:** XL+ (50h+, multi-week) · **Requires Ch:** all 13

A Grand Project sits alongside, not inside, this workbook's three Capstones (C-1/C-2/C-3): it is a fourth, optional, equally-serious synthesis exercise, sized and structured like a capstone (five phases, all chapters required, no named prerequisite concepts — figuring out the architecture is part of the assessment) but tackling a domain the Capstones don't touch. Like the Capstones, it deliberately does not name which event-loop, order-state-machine, or lock-free-ingestion architecture to use — that decision, and defending it, is the point. What *is* named, precisely, is the trading logic itself (see the Strategy Appendix): grading a strategy's profitability is not this project's job, and leaving entry/exit rules open would turn an engineering exercise into a trading-research one.

## Objective

Build a broker-agnostic algorithmic trading system for Indian cash-equity markets (NSE/BSE, whole shares only) that runs two fully-specified reference strategies against a deterministic historical replay in backtest mode, and against live market data with simulated fills in paper-trading mode — and *proves*, by test, that both modes produce bit-identical trading decisions given the same market data, rather than asserting it in a design document. Derivatives are entirely out of scope: no options, no futures, no margin/Greeks math, no lot sizes, no expiry cycles. The system trades cash equity, full stop.

This project is structured in five phases. Each phase has its own bar; do not move to the next phase until the current one's bar is met. A project that nails Phases 1–3 and documents honestly why Phases 4–5 weren't reached is a far stronger deliverable than one that rushes through all five with a shaky foundation.

## Strategy Appendix (fully specified — implement to spec, not by design)

**Strategy A — Dual Moving-Average Crossover with ATR Trailing Stop.**
- Entry (long only): `SMA(fast=20)` crosses above `SMA(slow=50)` on the daily bar, AND `ATR(14) > atr_floor` (a configured minimum volatility filter — reject entries in dead-quiet instruments where the stop would be meaninglessly tight).
- Position size: `qty = floor((equity * risk_frac) / (atr_mult * ATR(14)))`, where `risk_frac` (e.g. 0.01 = risk 1% of equity per trade) and `atr_mult` (e.g. 2.0) are configured constants. All arithmetic in integer paise/shares with an explicit, documented rounding rule — never floating-point division on the live decision path.
- Stop: trailing stop-loss at `high_water_mark − atr_mult * ATR(14)`, recomputed on every new bar's high, monotonically tightening (never loosens as price retraces).
- Exit: stop hit, OR `SMA(fast)` crosses back below `SMA(slow)` — whichever comes first.

**Strategy B — Mean Reversion on Rolling Z-Score.**
- Compute a 30-bar rolling linear regression of price against time; the residual (actual − fitted) at each bar, standardized by the residual's own 30-bar rolling standard deviation, is the z-score.
- Entry (long only): `z < -2.0`.
- Exit: `z > -0.5`, OR 20 bars have elapsed since entry (a hard time-stop — mean reversion that hasn't reverted in 20 bars is a thesis failure, not a delayed win).
- Position size: same formula as Strategy A, using the residual's rolling standard deviation in place of ATR as the risk unit.

Both strategies are long-only and intraday-or-short-swing by design — this keeps the reference implementation inside cash-equity CNC/MIS product semantics without touching short-selling mechanics (which have their own Indian-market-specific settlement wrinkles that are out of scope here). A student may design and add a third strategy against the same `IStrategy` interface as an optional extension, but is not required to.

## Phase 1 — Domain Model, Order State Machine, Deterministic Event Loop

Build the instrument/price/order domain model every later phase depends on. Prices and quantities are integer types throughout — paise and whole shares, never `double`/`float` on any path that affects a trading decision. Each instrument carries a tick-size field from the price-linked bucket schedule (currently: <₹250→₹0.01; ₹250–1,000→₹0.05; ₹1,000–5,000→₹0.10; ₹5,000–10,000→₹0.50; ₹10,000–20,000→₹1.00; >₹20,000→₹5.00 — reassigned monthly from the prior month's closing price, so this is a data table, not a hardcoded switch), a price-band percentage (2/5/10/20%, per-security), and a session-calendar classification distinguishing Closing-Auction-Session (CAS) instruments — which stop continuous trading at 15:15 and go through a structured closing auction to 15:35 — from non-CAS instruments, which trade continuously to 15:30. Pre-open is 09:00–09:15 for all instruments. Implement the order state machine covering the full documented status vocabulary (terminal: `COMPLETE`, `CANCELLED`, `REJECTED`; intermediate: at minimum `PUT ORDER REQ RECEIVED`, `VALIDATION PENDING`, `OPEN PENDING`, `OPEN`, `TRIGGER PENDING`, `MODIFY PENDING`, `MODIFIED`, `CANCEL PENDING`, `AMO REQ RECEIVED`) as a table-driven transition graph that explicitly tolerates unknown or skipped intermediate states — brokers document these as indicative, not contractual, and a state machine that asserts a fixed sequence will break the first time a real feed skips a state. Drive everything through a single-threaded, deterministic event loop that consumes a strictly-ordered event stream (ticks, order acks, timer events) and produces strategy decisions as a pure function of that stream: no wall-clock reads, no iteration over unordered containers on the decision path, no thread-local state. Exit bar: a test feeds the same recorded event stream through the loop twice, in separate process runs, and asserts byte-identical order-decision output both times; a separate suite exercises every documented state transition including at least three sequences with unexpected or skipped intermediate states, none of which deadlock the machine or misclassify a terminal state.

## Phase 2 — Strategy Interface, Risk Gate, Cost Model, Backtester

Define the `IStrategy` interface (`on_tick`, `on_order_update`, `on_timer`, each returning zero or more `OrderIntent`s) and implement both Strategy Appendix reference strategies exactly as specified — no discretionary tuning beyond the parameters the spec exposes as configuration. Build the risk gate as an ordered chain of pre-trade checks between strategy output and order submission: instrument tradability (session state accepts this order type now), price-band conformance, tick-size conformance, order-rate-limit compliance, position/exposure limits, available-margin/capital, a drawdown circuit breaker, and a kill switch — in that order, each with a distinct, machine-checkable rejection reason code (not a free-text string), since a test must be able to assert *which* check fired. Implement the transaction cost model computing STT (0.025% sell-side only for intraday/MIS, 0.1% both sides for delivery/CNC), NSE transaction charge (~0.00297%), SEBI turnover fee (₹10/crore), stamp duty (0.003% buy-side intraday, higher for delivery), brokerage (typically ₹20 flat or 0.03%, whichever is lower), and 18% GST applied to (brokerage + SEBI fee + transaction charge) only — GST does not apply to STT or stamp duty. Wire strategies, risk gate, and cost model into a backtester that replays a fixed historical tick file through the Phase 1 event loop, producing a deterministic equity curve and a per-trade ledger. Exit bar: both reference strategies run end-to-end over a multi-day recorded tape, producing an equity curve that is byte-identical across three separate runs, and a trade ledger whose computed costs match hand-calculated costs for at least five manually-verified sample trades spanning both CNC and MIS product types.

## Phase 3 — Live Market-Data Adapter, Simulated Fills, Backtest/Live Parity

Implement `IBrokerAdapter` as the broker-agnostic seam between the core and the outside world, and build two concrete pieces against it: a real, read-only live market-data adapter against one Indian broker's feed (a Kite Connect WebSocket-style binary feed is the natural reference — modes `ltp`/`quote`/`full` at 8/44/184 bytes, reconnect-tolerant), and `SimulatedBroker`, a student-built execution simulator that consumes the live tick stream and produces simulated fills using the identical fill logic the Phase 2 backtester applies against historical tape. This is the phase where the determinism argument below stops being an academic aside and becomes the thing you are graded on: the same strategy code, run once against historical replay and once against a recorded live session replayed through the exact same event-loop code path, must produce the identical sequence of `OrderIntent`s — proven by the parity test below, not claimed in prose. Exit bar: the parity test passes — a captured live session and a backtest replay of that same session's ticks produce byte-identical `OrderIntent` sequences with zero divergence — and the live adapter demonstrably reconnects and resumes correctly after a simulated feed disconnect without duplicating or dropping ticks into the event loop.

## Phase 4 — Hot-Path Latency

Take the tick-to-decision path — feed thread receives bytes, hands off to the core event loop, strategy evaluates, risk gate clears, order intent is queued for submission — and drive it to a stated, specific latency budget (e.g., a stated p99 tick-to-order-intent microsecond target under a stated synthetic tick-rate load), using a benchmark harness to establish the Phase 3 baseline *before* touching anything and to show each optimization's before/after delta. Replace the feed-to-core handoff queue with a lock-free structure only where profiling actually identifies it as the bottleneck; eliminate hot-path allocation (pre-sized ring buffers, pooled `OrderIntent`/tick objects) only where a profile shows it matters. This phase is explicitly not "rewrite everything to be lock-free" — if a profile shows the mutex-guarded queue isn't the bottleneck, it stays, and that's a correct engineering call, not a missed optimization. Exit bar: a documented latency report — methodology, stated target, measured p50/p99/p999 tick-to-decision latency under a specified load — meeting the stated budget, with at least one profile-identified bottleneck and a before/after fix backed by measured numbers.

## Phase 5 — Hardening, Reconciliation, Kill Switch, Real-Broker-Sandbox Proof

Harden against the failure modes that matter even for a paper-only system: feed disconnect/reconnect with tick-gap detection and resync; position reconciliation, where the system's internal position ledger is independently re-derivable from, and checked against, the broker's own position/order-history API on a schedule and at startup; a kill switch halting all new order submission on operator command or automatic drawdown-circuit-breaker trip, optionally triggering a flatten-all-positions sequence, reset only by explicit logged operator action; and rate-limit compliance against the broker's documented order/quote/historical throttles via a token-bucket limiter. The proof that `IBrokerAdapter` actually held as an abstraction — rather than being shaped by `SimulatedBroker`'s convenience by accident — is adding a second, real adapter against a broker sandbox that supports one (Upstox's sandbox is the current reference: order placement, cancellation, and status polling, no live capital at risk), implemented with zero modifications to the `IBrokerAdapter` interface or any strategy/risk/cost/core-loop file. Exit bar: the reconciliation check demonstrably catches an intentionally-injected position mismatch; the kill switch is demonstrated both operator-triggered and drawdown-triggered, each halting new submissions within a stated bound; and the sandbox adapter round-trips a real sandbox order through the unmodified strategy/risk/cost pipeline with zero changes to any file outside the new adapter's own directory.

## Constraints

- C++20. Cash-equity NSE/BSE instruments only — any options/futures/margin/lot-size/expiry-cycle logic appearing anywhere is scope creep to remove, not to harden.
- Prices and quantities are integer types end-to-end; a `double`/`float` anywhere on the price/quantity/P&L decision path is a defect. Enforce with a CI grep-gate, not a code-review promise.
- No third-party trading/broker SDK for the core engine, event loop, order state machine, strategy interface, risk gate, or cost model — this project's value is in designing and building those yourself. A minimal HTTP/WebSocket client library is acceptable for the adapter layer specifically (the adapters are glue, not the assessed core).
- **Paper-only enforcement — layered, defense-in-depth, no single point of failure:**
  1. *Compile-time*: a `TRADING_MODE` build option defaulting to `PAPER`; a `LIVE` configuration does not exist in any default entry in `CMakePresets.json` and must be hand-added by someone who has read the constraints below.
  2. *Runtime guard*: any adapter capable of placing a real order (the Upstox sandbox adapter included) constructs its transport layer only after checking a runtime `AllowRealOrders` flag, `false` unless explicitly set — the compile-time flag alone is not trusted.
  3. *Config token*: a `LIVE`-mode config additionally requires a specific, non-default confirmation token the operator must copy from documentation — never a plain boolean.
  4. *Startup abort window*: any `LIVE`-mode startup prints an unambiguous warning and blocks for a configurable delay (e.g. 10 seconds) during which Ctrl-C aborts cleanly, before the adapter's transport layer is even constructed.
  Removing any one layer alone must not be sufficient to enable real order placement.
- Must build and run correctly on both the MSVC and WSL-GCC/Clang toolchains.
- Every phase's exit bar must be met with an actual demonstrated test, not a design-document claim.

## Documentation Deliverable

Alongside the code, a design document explaining: the chosen event-loop and order-state-machine architecture and why (with at least one credible alternative named and why it wasn't chosen), the determinism argument as actually implemented (which of the seven sources of nondeterminism applied to this codebase, and the specific mechanism eliminating each), the risk gate's check ordering and why that order, and an honest accounting of which phases were fully reached and which were partially or not reached, with reasons.

## Acceptance Criteria

- Phase 1 through Phase 3's exit bars are met in full; Phases 4–5 attempted to whatever extent time allows and honestly documented either way.
- The Phase 1 deterministic-replay test (byte-identical decisions across repeated runs of the same event stream) passes.
- Both reference strategies run correctly end-to-end in the Phase 2 backtester, with the cost model's output verified against hand-calculated sample trades.
- The Phase 3 backtest/live parity test passes with zero divergence over at least one full captured trading session.
- If Phase 5 is attempted: the kill switch and drawdown circuit breaker are each demonstrated tripping correctly under an injected scenario, and the sandbox adapter round-trips a real order through the unmodified strategy/risk/cost pipeline.
- A grep-based CI check confirms zero `double`/`float` usage on the price/quantity/P&L decision path.

## Hints

### Hint 1 — Direction
Do not start by wiring up a real broker feed. Start entirely offline: build Phase 1's domain model and event loop against a hand-written, tiny, fully-controlled synthetic tick sequence you author yourself, and get the determinism test passing against that before any real market data enters the picture. The temptation with a "trading system" project is to chase realism (real feeds, real brokers) before the deterministic core is trustworthy — resist it; an unreliable foundation makes every later bug ambiguous between "logic bug" and "nondeterminism," and by Phase 3 you'll have two live and two replay paths to debug at once if the core wasn't proven solid first.

### Hint 2 — Technique
The single hardest discipline in this project is banning `now()` from the decision path, and the natural failure mode is a well-meaning timeout or staleness check quietly calling it from deep inside strategy or risk code. Thread a `Clock` interface through every constructor that needs time, with exactly two implementations — `ReplayClock` (returns the current event's recorded timestamp) and `LiveClock` (a thin wrapper over the feed's own timestamps, never the local machine's) — and add a CI grep-check banning direct calls to `std::chrono::system_clock::now()`/`steady_clock::now()` outside a small, explicitly allowlisted set of files (the adapters themselves, which legitimately need wall-clock for reconnect backoff timing, not for trading decisions).

### Hint 3 — Implementation
Build the tick-size and session-calendar tables as data, not code — a per-instrument record loaded from a config file (refreshed monthly for tick size, per-exchange-calendar for sessions), never a hardcoded switch statement on price ranges or a hardcoded 15:15/15:30 literal buried in the event loop. Treat every other broker-specific numeric threshold (band percentages, rate limits, MIS auto-square-off time — which is broker risk policy and changes) the same way: configuration the risk gate and `SimulatedBroker` read, never constants compiled into the binary.

### Hint 4 — Debugging/Design
If the Phase 3 parity test fails with a divergence, resist the urge to add a tolerance window ("prices within 1 paisa count as matching") to make it pass — that tolerance would be hiding exactly the bug the test exists to catch. Instead, binary-search the tick log: replay progressively longer prefixes of the captured session through both paths until you find the shortest prefix that still diverges, then inspect that prefix's last few ticks by hand. In practice this narrows to one of a small number of causes — two ticks sharing an exchange timestamp processed in different relative order between the live handoff queue and the backtester's tape iteration, or a risk-gate check reading a mutable "now" instead of the current event's timestamp — and the fix is never a tolerance, it's finding and removing the specific nondeterminism source.
