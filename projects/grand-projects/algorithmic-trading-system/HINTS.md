# GP-1 — Hints

## Hint 1 — Direction

The pull of this project is toward realism first: wire up a real broker WebSocket feed, watch live ticks flow, feel like you're building "a real trading system." Resist it, in this order:

Start entirely offline. Author a tiny synthetic tick sequence by hand — a plain text or CSV file you write yourself, not downloaded, not generated — with maybe 20-50 events covering a couple of instruments, at least one pair of events sharing an exchange timestamp, and a couple of order-status transitions you deliberately construct to be adversarial (a skipped intermediate state, a cancel racing an ack). Get Phase 1's event loop and state machine passing the determinism test against *only* this file before writing a single line that touches a network socket.

The reason this ordering matters is diagnostic, not aesthetic. Once a real feed is in the loop, every bug you hit has two candidate explanations: "my core logic is wrong" or "the feed is misbehaving in some way I didn't anticipate (out-of-order packets, a reconnect duplicating a tick, a timestamp that isn't monotonic)." If the core was proven deterministic and correct against a source you fully control first, any bug that shows up after the feed is wired in is almost certainly a feed-handling bug, not a decision-logic bug — and you'll know where to look immediately instead of re-auditing everything.

This also naturally forces the right abstraction boundary: if your event loop can only be fed by "a live socket," you've coupled it to I/O by construction, and Phase 3's parity test becomes hard to even express. If it can only be fed by "an ordered stream of events, however produced," backtest and live are the same consumer from day one and parity is nearly free.

## Hint 2 — Technique

The single most common way this project's core promise ("backtest and live produce identical decisions") quietly breaks is a wall-clock read smuggled into decision logic — almost never on purpose. It looks like: a staleness check ("is this quote older than 500ms? if so, skip it") that calls `std::chrono::steady_clock::now()` directly because that's the obvious way to write a staleness check. In backtest, "now" is meaningless — there is no wall clock, there's only "the timestamp of the event currently being processed." In live replay, "now" is real, and will differ run to run by definition. The moment any decision-path code reads real wall-clock time, backtest and live have diverged by construction, and no amount of careful strategy-logic debugging will find it, because the bug isn't in the strategy logic.

The fix is to make "now" a first-class, injected dependency rather than an ambient global. Define a small `Clock` interface with one method returning the current logical timestamp. Provide exactly two implementations: `ReplayClock`, which simply returns the timestamp carried by whatever event the loop is currently processing (so "now" during replay is always a value that came from the event stream itself, never the machine's clock), and `LiveClock`, which is a thin wrapper that also derives its "now" from the feed's own timestamps rather than the local machine's clock — even in live mode, prefer the exchange's timestamp on the packet over `system_clock::now()`, since the two can and do drift, and the exchange's timestamp is what a backtest replaying the same session would see. Thread a `Clock&` through every constructor of every class that has any legitimate reason to ask "what time is it" — strategies, the risk gate, the event loop itself.

Then make the discipline enforceable, not just documented: add a CI step that greps the source tree for `system_clock::now()` and `steady_clock::now()` outside a short, explicit allowlist of files (the live adapter's reconnect-backoff logic is a legitimate exception — deciding how long to wait before retrying a dropped connection is not a trading decision and correctly uses real wall-clock time). A grep-gate here is worth more than a code-review comment, because this specific bug is exactly the kind that's easy to introduce eight files away from where anyone is looking, six weeks into the project, under time pressure in Phase 4.

## Hint 3 — Implementation

Every Indian-market-specific numeric fact in this project's domain — tick-size buckets, price-band percentages, the CAS/non-CAS session-hours split, MIS auto-square-off time, broker rate limits — is something that has changed at least once in the recent past and will change again. Tick-size buckets are reassigned monthly from the previous month's closing price. The CAS market-hours split itself is only months old as of this project's writing. MIS square-off time has moved more than once in the last year, purely as broker risk policy, with zero code-level trading-logic implication.

Treat every one of these as configuration data the risk gate and `SimulatedBroker` read at startup (or reload periodically, for the tick-size table), never as a literal embedded in a conditional. A hardcoded `if (price < 250) tick = 1;` or a hardcoded `if (time >= 15:15) session = CAS_CLOSING;` will pass every test you write today and quietly become wrong the next time NSE issues a circular — and worse, it'll be wrong silently, producing a plausible-looking but incorrect tick-size or session classification rather than an obvious crash. A per-instrument record loaded from a small config file or table, refreshed on the cadence the real data actually changes on, turns "the market changed a rule" into "update a data file" instead of "find and fix a scattered set of conditionals."

This same discipline applies to the four-layer paper-only enforcement in Constraints: the confirmation token, the abort-window delay, and the runtime guard default should all be configuration values with documented, deliberately inconvenient defaults — not constants baked into the binary that would require a rebuild (and thus a moment of "wait, why am I rebuilding this" friction) to even attempt to change.

## Hint 4 — Debugging/Design

When the Phase 3 parity test fails, the almost-irresistible first instinct is to add slack: "prices within 1 paisa should count as matching," or "allow the order sequences to differ if the net position ends up the same." Do not do this. That tolerance doesn't fix the divergence — it hides it, and it specifically hides it in exactly the place this test exists to catch it. A parity test with a tolerance window is a test that no longer tests parity; it tests "approximately similar," which was never the requirement.

Instead, treat it as a bisection problem. Take the captured session's tick log and replay progressively longer prefixes — first 10 events, then 100, then 1,000 — through both the live-shaped path and the backtest path, and find the shortest prefix where the two still diverge. This will typically narrow down to a handful of events very quickly, and at that scale you can read every field of every event by hand. In practice, when this test fails, the cause is almost always one of a small number of things: two ticks that share an identical exchange timestamp being processed in a different relative order by the live handoff queue than by the backtester's linear tape iteration (a genuine ordering ambiguity in the source data that your event loop needs an explicit, documented tie-breaking rule for — e.g. "ties broken by arrival sequence number, not timestamp"); a risk-gate check that reads some form of mutable "current time" instead of the timestamp carried by the event actually being evaluated (see Hint 2); or a container iterated in an order that isn't guaranteed stable (an `unordered_map` walked for, say, "check all open orders," where insertion-order-dependent iteration silently produced a different check order between two runs). In every one of these cases, the fix is to find and eliminate the specific nondeterminism source at its origin — never to widen the test's tolerance to stop noticing it.

If you get stuck narrowing the divergence, it's worth writing a small dedicated diff tool once, rather than eyeballing two long `OrderIntent` logs by hand repeatedly — a script or test helper that takes both sequences and prints the first index where they differ, field by field, will pay for itself many times over across this project's remaining phases, since Phase 4's optimization work is exactly the kind of change likely to reintroduce a subtle ordering bug that only this test would catch.
